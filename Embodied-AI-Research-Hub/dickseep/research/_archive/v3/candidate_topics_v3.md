## 候选 1（主线，最低依赖）：执行长度的**实现语义**与同步预算

### 一句话

同一个 `E`，上游代码执行的是**后缀**；把它改成前缀后，成功率与预算都会变 —— 那么文献里报告的「执行长度效应」，有多少其实是**起始槽偏移**造成的？

### 科学问题

1. 在**同一 checkpoint、同一仿真、同一硬件**下，`original_suffix` 与 `corrected_prefix` 两种实现语义，对成功率、动作平滑度、墙钟预算的**影响是否可分辨**？（`E=P` 处两者必然相同，可作内部锚点）
2. 在同步执行入口下，给定目标控制周期 `Δt_target`，哪些 `E` 满足平均速率预算 `L ≤ E[Δt_target − (s+h)]`？不满足时，成功率如何随「预算缺口」变化？
3. 「执行长度效应」在多大程度上可**分解**为：起始槽偏移（实现）+ 重规划频率（架构）？

### 已有工作（边界）

| 工作 | 做了什么 | 没做什么（在检索边界内） |
|---|---|---|
| KWS（2609.00908） | 扫固定 `E`（LIBERO 2/4/6/8/10），报延迟 A100 0.2661 s、真机 60 Hz | **未声明所用实现语义**（后缀/前缀），也未把延迟与 `E` 连成判据 |
| AAC（2604.04161） | 自适应 `E`，报推断时间 83–157 ms | 未讨论实现语义；GPU 未声明 |
| VLAQuantBench（2609.25376） | 指出「`P` 与 `E` 必须区分」，做过 1 次 `50 vs 10` 扰动 | 未讨论「保留前 E 还是后 E」 |
| V14（本地审计） | 发现上游是后缀，给出前缀修复与预算公式 | 未做真实实验（无权重、无 GPU） |

> [!note] 这一条的「新」在哪里，以及不新在哪里
> **不新**：扫 `E`、测延迟、区分 `P`/`E` 都已有人做。
> **候选新增**：把「实现语义」当作**必控因子**，并用 `E=P` 锚点做内部对照，从而把「`E` 效应」分解为「槽偏移 + 重规划频率」。
> `🟥` 该分解在此检索边界内未见报告；但**不能**因此称为原创——它也可能是没人认为值得报。

### 预期贡献（候选）

1. 一份**索引契约**（可执行断言）：`1≤E≤P`、首执行槽 = 0、连续槽 = 0…E−1、输出长度 = P。
2. **双实现对照**的成功率/平滑度/预算表；`E=P` 作共同锚点。
3. 同步入口下的**预算判据**与 deadline miss 统计（p50/p95/p99 + 边界间隔）。
4. 一条工程结论：**报告 `E` 时必须同时报告实现语义**，否则数字不可复现。

### 最小实验

- 因子：`impl ∈ {suffix, prefix}` × `E ∈ {8, 4, 2, 1}`（`E=8` 为重合点）× 1 个 LIBERO 套件（建议 Spatial 或 Long）。
- 每组：固定初始状态集，逐 episode 记录成功/失败、执行槽序列、`L`、`step_wall`、块边界间隔。
- 8 格 × 配对，先做 `E=8` 与 `E=4` 两格判方向，再决定是否补 `E=2/1`。

### 资源需求

| 项 | 需求 |
|---|---|
| GPU | 单卡 12GB（**前提：所选基座 bf16 能进 12GB**，见准入分级） |
| 训练 | **无** |
| 依赖 | PyTorch + 该基座官方推理栈 + LIBERO（需批准，见 `advisor_one_page.md`） |
| 时间 | 6–8 人周（含 Gate 0 与准入分级） |
| 存储 | 权重 + 仿真资产（GB 级） |

### 失败退路

| 若… | 则… |
|---|---|
| 两实现对 `SR` 无可分辨差异 | 结论改为「`E` 效应不是实现伪影」，仍是有效判定；转向候选 3 的准入基准 |
| 基座 bf16 进不了 12GB | 降到候选 3；或申请服务器 |
| 仿真评测太慢 | 只做 1 套件 × 子集，先出方向性结论，明确标注「子集，非全套」 |

## 候选 2（增量创新，需可加载基座）：量化方式 × 执行长度的**交互**

### 一句话

量化惩罚不是常数：它会随「开环执行多久」变化吗？而这个变化在两个实现语义下是否一致？

### 科学问题

1. 在同一基座上，`ΔSR(E) = SR_quant(E) − SR_ref(E)` 是否随 `E` 增大而变负（交互效应）？
2. 该交互是否**依赖实现语义**（suffix vs prefix）？若依赖，则以往把 `E` 当常数的量化评测都可能被实现语义污染。
3. 若交互存在，能否给出一条**部署规则**（如「量化后应减小 `E`」）并有实测支持？

### 已有工作（边界）

| 工作 | 做了什么 | 与本题的关系 |
|---|---|---|
| QVLA（2602.03782）§3.2 | 提出 cumulative sensitivity，把「误差累积」用于**比特分配** | **机制先行**。本题**绝不**声称首次发现累积 |
| VLAQuantBench（2609.25376） | 层范围×格式×校准三因子；单输出投影保护；闭环 200 episodes/格 | 覆盖了「敏感性+保护」；但 `E` 固定 |
| QuantVLA（2602.20309） | 选择性布局 + 两个校准标量；扫**去噪步数** | 未扫执行长度 |
| BitVLA（2506.07530） | 1-bit QAT | 未报 `E` |

> [!warning] 措辞红线（继承 R2 §4）
> ❌ 不得写「首次发现量化误差累积」；❌ 不得写「提出累积敏感度」。
> ✅ 只能写：「**量化方式与执行长度的交互效应**，在本次检索边界内未见作为实验因子研究」。

### 预期贡献（候选）

1. `量化方式 × E × 实现语义` 的交互表（小规模、配对）。
2. 若交互显著：给出「量化后 `E` 的推荐区间」及其预算含义。
3. 若交互不显著：给出「量化惩罚近似与 `E` 无关」的边界条件——这同样是有用结论。

### 最小实验

- 因子：`quant ∈ {bf16, W8, W4}` × `E ∈ {8, 4, 1}`，**先固定 `prefix`**，`suffix` 作一组消融。
- 每组 1 套件、固定初始状态、配对。
- 先做**离线动作误差**预筛（同一观测下 `‖a_quant − a_bf16‖` 随块内位置 `k=1..P` 的变化），成本低，可提前止损。

### 资源需求

| 项 | 需求 |
|---|---|
| GPU | 单卡 12GB，**且 bf16 参照必须能在同卡运行**（否则对照不成立，见 §4.3） |
| 量化 | PTQ（训练无关）；**模拟量化只能报误差，不能报显存/延迟** |
| 时间 | 9–11 人周 |
| 前置 | 候选 1 的索引契约 + 准入分级 |

### 失败退路

| 若… | 则… |
|---|---|
| bf16 基座进不了 12GB | **不做**（跨机 SR 不默认等价）；转候选 1 或 3 |
| 4-bit 直接掉到 0 | 只做 W8 vs bf16 的交互；结论限定比特宽 |
| 交互不显著 | 写成「量化惩罚与执行长度无关」的边界结论，附预算含义 |
| 动作头无 kernel | 只做模拟量化，**明确不报显存/加速** |

## 候选 3（兜底，最低风险）：12GB 上的**准入分级**与预算基准

### 一句话

「能加载」「能推理」「能评测」是三件事；在 12GB 消费级卡上，候选基座分别卡在哪一级？

### 科学问题

1. 对候选基座（SmolVLA、π0.5、以及 OFT 作参照），在 RTX 5070 12GB 上分别能否通过**可加载 / 可推理 / 可评测**三级？
2. 卡点是什么：显存、依赖/算子（sm_120）、仿真评测吞吐，还是数值（NaN/dtype）？
3. 在通过的配置上，`L`、`step_wall`、`H`、块边界间隔的分布如何？对应 `Δt_target` 的 deadline miss 率是多少？

### 已有工作（边界）

- VLAQuantBench Table 10 给了 **4090** 上的 BF16 15.0 GiB（OFT，仅 LLM 量化场景的 BF16 基线），**不是 12GB，也不是 5070**。
- 无任何工作在 **RTX 5070 12GB** 上报告 VLA 的准入与预算。`🟥` 但这是「没人报」而非「没人能做」。

### 预期贡献（候选）

1. 一张**三级准入表**（基座 × 级别 × 卡点），附可复现判据。
2. 一份**测量脚本**（`L`/`step_wall`/`H` 分解、p50/p95/p99、块边界间隔、rho_infer）。
3. 对候选 1/2 的**可行性裁决**：哪些题在无服务器条件下可做。

### 最小实验

对每个基座跑：加载 → 单次前向（shape/dtype/NaN）→ 1 个 LIBERO episode。每级记录通过/失败与卡点。

### 资源需求

- 单卡 12GB；无训练；时间 3–4 人周（含 Gate 0）。
- 需批准下载权重与仿真资产。

### 失败退路

- 若全部基座都过不了「可评测」→ 结论本身成立（12GB 不可行），毕设转为**测量协议 + 负结果**，仍有交付价值。

## 三题对比与推荐

| 维度 | 候选 1（语义+预算） | 候选 2（量化×E） | 候选 3（准入基准） |
|---|---|---|---|
| 是否需训练 | 否 | 否 | 否 |
| 12GB 可行性 | 中（取决于基座） | **低**（需 bf16 同卡参照） | **高** |
| 需服务器 | 否 | **是（强烈建议）** | 否 |
| 新颖性（候选，非声明） | 中 | 中 | 低 |
| 失败仍有产出 | ✅ | ✅ | ✅ |
| 与博士衔接 | 强（测量基础设施） | 很强（量化主线） | 强（准入基线） |
| 体量 | 6–8 周 | 9–11 周 | 3–4 周 |

**推荐**：**候选 3 → 候选 1 → （有服务器再上）候选 2**。
即：先花 3–4 周把准入与预算测清楚（这一步同时产出可复用的 `measure.py`），再进入候选 1 的双实现对照；候选 2 作为有服务器时的增量。

`🟥` 三个题目的创新性均**未经验证**，只能作为「候选」进入讨论，不得写入开题报告的主张栏。
