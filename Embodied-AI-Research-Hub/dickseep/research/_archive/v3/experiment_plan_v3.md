# 实验方案 v3

> [!warning] 与 v2 的三处根本差别
> 1. **`E` 不再是「执行前 E 步」那么简单**：上游代码执行的是**后缀**（V14 F2）。v3 把「实现语义」列为**必控因子**。
> 2. **时序模型换成同步的**：`max(E·Δt, L)` 与「`L≤P·Δt` 就能不间断」**作废**（V14 F3），改用 `T_block = L+S+H`。
> 3. **跨 GPU 的成功率不默认等价**（v2 曾允许跨机锚定，v3 收紧）。

---

## §0 术语与变量（V14 为准）

| 变量 | 含义 | 能否改 | 备注 |
|---|---|---|---|
| `P` | 一次模型调用预测的时间步数 | ❌ 固定（LIBERO=**8**，ALOHA=25，BRIDGE=5） | 改 `P` 等于改预测接口，**禁止**用它来扫 `E` |
| `D_a` | 每步动作维度 | ❌ | LIBERO=**7** |
| `E_cfg` | `num_open_loop_steps` 配置值 | ✅，但 `1≤E_cfg≤P` | 作为 deque 的 `maxlen` |
| `E_run` | 某块实际 `env.step` 次数 | 运行期决定 | `done`/异常/步数上限会使其 **< E_cfg** |
| `slot` | 块内预测时间槽索引 0…P−1 | — | **上游实现首执行槽 = P−E**，这是本题核心 |
| `Δt_sim` | 一次 `env.step` 推进的仿真时间 | ❌ | 来自 LIBERO/robosuite 配置；`🟥` 本会话未加载 |
| `Δt_wall` | 一次 `env.step` 的墙钟耗时 | ❌（只能测） | 含物理/渲染成本 |
| `L` | `get_action` 调用到完整动作列表可用的墙钟延迟 | ❌（只能测） | **不含** `prepare_observation` |
| `H` | 每步除 `get_action`/`env.step` 外的串行开销 | ❌ | `prepare_observation`、队列操作、`process_action`、`tolist` |
| `Δt_target` | 拟部署执行器的目标墙钟控制周期 | 外部参数 | **不是**代码保证的周期；OpenFleX 未知（🟥） |

**禁止混用**：`Δt_sim ≠ Δt_wall ≠ 视频 fps ≠ 1/control_freq`（V14 明确）。本方案里凡出现 `Δt` 必注明是哪一个。

## §1 同步时序模型（替代 v2 的异步公式）

### 1.1 现状（V14 F3，已核实）

所审 LIBERO 入口是**同步阻塞**：队列空 → 阻塞推理 `L` → 再逐个 `env.step`。**推理与执行不重叠。**

### 1.2 可用公式（🟨 推导，须以实测校验）

```
T_block      = L + S + H            # S = Σ step_wall, H = Σ 每步其他开销
f_exec       = E_run / T_block       # 执行频率
f_replan     = 1 / T_block           # 重规划频率
ρ_infer      = L / T_block           # 推理阻塞占比
平均速率预算  : L ≤ E[Δt_target − (s+h)]        # s,h 为每步均值
所需最小 E   : E_min(Δt_target) = ceil( L / (Δt_target − (s+h)) )
```

**这套式子替代 v2 的 `E/max(E·Δt, L)`。** 后者的前提（重叠）在现状下不存在。

### 1.3 必须报的量（缺一不可）

| 量 | 口径 | 注意事项 |
|---|---|---|
| `L` | p50 / p95 / p99，≥200 次，warmup 20 | 必须 `torch.cuda.synchronize()` 后计时 |
| `step_wall` | 同上 | 与 `Δt_sim` **分开报** |
| `H` | 逐项分解（prepare/queue/process/tolist） | 只报总和无法定位瓶颈 |
| **块边界间隔** | 上一块最后一步 → 下一块第一步 | 这是同步架构的**最坏单步间隔** |
| `f_exec` / `f_replan` / `ρ_infer` | 由上式算 | 不等长 episode 用「总动作数/总墙钟」 |
| **deadline miss 率** | 对给定 `Δt_target`，块边界间隔超周期比例 | 比平均值更能说明问题 |

> [!caution] 三条禁止
> ❌ 用 `sleep` 制造延迟来「模拟实时」——`env.step` 驱动的仿真在等待时**世界不推进**，sleep 只拉长墙钟（V14）。
> ❌ 把 `ρ_infer` 说成「GPU 空闲」或「机器人静止」——它只表示调用方没送出新动作。
> ❌ 用 `U = SR×(1−idle)` 冒充吞吐；真实吞吐另报「成功 episode 数 / 总墙钟时间」，并声明超时与 reset 成本。

## §2 必控因子：实现语义（`original_suffix` vs `corrected_prefix`）

### 2.1 问题（V14 F2）

`deque(maxlen=E)` + `extend(actions)` ⇒ 保留的是**后 E 个**。所以：

| `E` | 上游实际执行槽 | 修正后应执行槽 |
|---|---|---|
| 8 | 0…7 | 0…7（**重合**） |
| 4 | 4…7 | 0…3 |
| 2 | 6…7 | 0…1 |
| 1 | **7** | 0 |

**后果**：只改 `num_open_loop_steps` 得到的曲线，同时改变了「执行次数」与「起始槽偏移 `P−E`」，**两因素混杂**。

### 2.2 实验包装层的索引契约（G4，可执行断言）

```python
# 独立包装层；不改官方仓库
E = cfg.num_open_loop_steps
assert 1 <= E <= NUM_ACTIONS_CHUNK
actions = get_action(...)
assert len(actions) == NUM_ACTIONS_CHUNK
assert all(a.shape == (7,) for a in actions)      # 仅 LIBERO
assert len(action_queue) == 0
action_queue.extend(actions[:E])                   # ← 前缀修复（原为 actions）
```

两种实现都必须能跑，作为**两个臂**：

| 臂 | 入队写法 | 首执行槽 |
|---|---|---|
| `suffix`（上游） | `extend(actions)` | `P−E` |
| `prefix`（修正） | `extend(actions[:E])` | `0` |

🟦 `E=P` 时两臂**逐位相同** ⇒ 天然的**共同锚点**，也是唯一不受该缺陷影响的配置（V14 建议的 baseline）。

### 2.3 逐动作元数据（必须记录）

每条执行动作记：`prediction_id`、`source_observation_step`、`predicted_slot`、`execution_step`、墙钟时间戳、触发推理时的 `remaining_queue`。
没有这张表，「槽偏移」与「陈旧度」都无法事后归因。

## §3 准入分级（G1–G3）：先证明能跑，再谈选题

> 目标：把「能加载 / 能推理 / 能评测」拆成三级，逐级给通过判据。**任何一级不过，就不做依赖它的题。**

| 级 | 判据 | 记录 | 失败即停 |
|---|---|---|---|
| **G0 环境** | `torch.cuda.get_device_capability()` = (12,0)；CUDA/PyTorch/驱动版本；最小张量前向 | 版本表 | 全线阻塞 |
| **G1 可加载** | 权重可下载；`max_memory_allocated < 12 GiB`；无 OOM | 峰值显存、精度、加载耗时 | 该基座淘汰 |
| **G2 可推理** | 前向输出 `[P, 7]`；dtype 正确；**无 NaN/Inf**；重复 10 次一致 | 输出 shape/dtype、`L` 的 p50/p95 | 该基座淘汰 |
| **G3 可评测** | LIBERO 1 套件 1 episode 完整跑通；能产出成功/失败 | 每 episode 墙钟、`step_wall`、`H` | 只用 G1/G2 做候选 3 |

## §4 统计方案

### 4.1 设计

| 要素 | 规定 |
|---|---|
| 实验单元 | task |
| 配对单元 | (task, init state) —— LIBERO 用固定初始状态集 |
| 重复 | 每格 ≥ 1 次全套件评测；关键格 ≥ 2 个评测 seed |
| 区组 | 按 suite 分报，不跨 suite 混算 |
| 主分析 | 配对：McNemar（成功/失败）；配对 bootstrap 给风险差 CI |
| 主指标 | **成功率**（预设）；次指标：`f_exec`、`ρ_infer`、块边界 p95、deadline miss 率、jerk |
| 多重比较 | Holm |
| 禁止 | ❌ 用两个 CI 是否重叠代替检验；❌ 只在事后挑指标 |

### 4.2 功效（沿用 R2 的复算）

| 场景 | 需要的样本 |
|---|---|
| 独立两组，检 5 pp（p≈0.5） | ≈1,570 /组 |
| 独立两组，检 10 pp（p≈0.5） | ≈393 /组 |
| **配对 McNemar，检 5 pp（不一致率 0.10）** | **≈312 对** |
| 配对，检 10 pp（不一致率 0.10） | ≈77 对 |
| 单组 95% CI 半宽（n=500, p=0.9） | ±2.6 pp |

⇒ 一个套件 500 episode 的**配对**设计足以检 5 pp；**独立**设计不够。这是必须用配对的原因。

### 4.3 跨 GPU：不默认等价

| 主张 | v2 | **v3** |
|---|---|---|
| 同一配置在两块 GPU 上成功率相同 | 曾允许「跨机锚定」 | ❌ **不默认等价** |
| 延迟可比 | 不可 | 不可（维持） |

**若确需跨设备比较成功率**，必须先做一次**等价性检查**（不是假设）：

1. 同一 checkpoint、同一 seed、同一初始状态集，在两块 GPU 上各跑一遍；
2. 逐 episode 比对成功/失败是否一致；
3. 报不一致 episode 比例与方向；
4. 只有在不一致率足够低（阈值需预先设定，例如 <2%）且方向随机时，才允许做**带声明的**跨设备合并；否则**分设备报告**。

该检查本身耗时，因此**默认路线是单设备内完成所有比较**（这也是候选 2 需要 bf16 同卡参照的原因）。

## §6 两条路线

### 6.1 路线 A：**无服务器**（默认）

```text
G0 环境
  └─ 候选3 准入分级（SmolVLA / π0.5）
       ├─ 有基座过 G3 ──→ 候选1（双实现对照，1–2 套件）
       └─ 全部不过 ────→ 毕设转为「准入基准 + 测量协议 + 负结果」
```

- **候选 2 不在路线 A 内**（需要 bf16 同卡参照，12GB 上 OFT 不可行）。
- 最低可交付：准入表 + 索引契约 + 双实现对照表 + 预算表 + `measure.py`。

### 6.2 路线 B：**有服务器**（扩展）

```text
路线 A 的全部
  + OFT-7B bf16 在服务器上跑参照（仅 SR；跨设备须先做 §4.3 等价性检查）
  + 候选2：量化 × E 交互（服务器或 5070 上 bf16 可跑的基座）
  + 可选：把异步定速执行作为独立架构因素（需另写执行器，风险高，不建议本科做）
```

⚠️ 服务器路线**不解除** §4.3：跨设备 SR 仍需等价性检查，或分设备报告。

## §9 本方案的边界

1. **`Δt_sim` 未核实**：本会话未加载 LIBERO/robosuite，控制频率与后台推进语义仍 `🟥`。
2. **无任何实测**：所有数值推导都需 G1–G3 校验后才可用。
3. **不继承 v2 的异步公式**；异步是待实现架构（V14 §5.3），本轮不设计。
4. **不假设 OpenFleX 的 `Δt`**：用 `E_min(Δt_target)` 参数化，而非代入单一目标周期。
5. **不把「文献未报告某变量」当作原创依据**。
