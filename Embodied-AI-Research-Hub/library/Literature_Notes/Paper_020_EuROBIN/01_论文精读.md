# P020 · 异构机器人团队的门到门包裹配送（euROBIN 黑客松）

> [!abstract] 一句话先给你
> **8 台形态完全不同的机器人（工业臂、两种人形、两种移动操作臂、Centauro、轮腿四足、空中操作臂），在 5 天黑客松里接力把一件包裹从"供应点"送到"用户家里"，全程 18 分钟。** 这不是一篇提出新算法的论文，而是一份**真实多机系统的集成报告 + 踩坑清单**——而它的"坑"恰恰是我做具身系统架构时最该提前知道的。

> [!info] 这是一篇**黑客松报告**，不是方法论文
> 它**没有提出新算法、没有消融实验、没有统一基准**。02 笔记的"创新"一节按"系统集成 + 经验总结"的标准写。
> 我精读了：引言、场景、8 个平台、各机器人功能、联合实验、**逐队"lessons learned"**、总体教训、结论。

## 二、三种长度的摘要

### 2.1 30 秒摘要（约 160 字）

物流的完整链条——打包、运输、送达、拆包——通常由人完成。euROBIN 想验证"全机器人"可行：8 个欧洲团队带 8 台机器人，在 5 天里搭出一条接力链。工业臂打包，Centauro/空中臂/轮腿四足负责运输，两个人形 + 两个移动操作臂负责送达与拆包。最终实验 18 分钟跑通，但**空中交接与开门仍需遥操作**。

### 2.2 3 分钟摘要（约 480 字）

**问题。** 最后一公里配送已有大量研究，但"从供应点到用户家里"的**完整链条**（打包 → 运输 → 家门口 → 拆包）需要**异构机器人协作**：轮式的跑平地、腿式的上楼梯、空中的跨障碍、双臂的操作。这种系统集成在真实场景里几乎没人完整跑通过。

**做法。** 不是提算法，而是**组织一次黑客松**：8 个团队、8 台机器人、3 个域。
1. **打包域**（供应点）：**Franka Emika FR3** 工业臂，从料箱里抓取物体、装进包裹箱、封箱。
2. **运输域**：**Centauro**（轮腿混合、双臂）、**空中操作臂**（多旋翼 + 双臂）、**ANYmal on Wheels**（轮腿四足）。
3. **送达与拆包域**（家居）：**Rollin' Justin**、**ARMAR-6**（两个人形）、**TIAGo-1**、**TIAGo-2**（两个移动操作臂）。

**接口。** 用 **ROS 2**（自动发现）、**ROS 1/ROS 2 桥**、以及 **ArmarX 的 RESTful API** 做跨团队通信；门是"传感器化"的（M5Stack Core 2），通过 ROS 2 topic 交互。

**结果与教训（本文最有价值的部分）。**
- **最终实验 18 分钟**跑通，**无直接人工干预**，但**空中交接与开门把手使用了遥操作**；
- **任务定义是在黑客松期间现场定的**，团队没有前期准备时间——所以时间数字不代表系统极限；
- **操作类任务普遍偏慢**，作者明确说"需要提升执行速度，尤其是操作"；
- **逐队教训**（见 §五）：
  - **Franka**：依赖"已知 3D 模型 + 仿真物体-夹爪交互"，物体多样性一大就不适用；
  - **Centauro**：从水泥地进到飞行区的**泡沫地板**，摩擦骤增 → 腿部关节内应力 → 驱动器温度危险上升；
  - **空中操作臂**：**旋翼下洗气流**在 <1 m 距离把纸箱吹跑（前 3 次抓取失败）；空箱时"钟摆效应"导致掉落失败；>5 m 视距时人眼分不清末端与把手（建议加 FPV 相机）；
  - **ANYmal on Wheels**：轮腿模式速度更高、能耗更低；但需要**预先建图 + 数字孪生**，准备工作量大；
  - **通信**：多套 Wi-Fi + 参与者手机移动数据互相干扰 → 最后**要求所有人开飞行模式**。

**结论。** 全机器人门到门配送**技术上可行**，但**瓶颈不在单个机器人的能力，而在接口、准备时间、以及"人机混合"的兜底**。未来工作指向 EuroCore 仓库——让机器人之间**共享地图与技能**。

### 2.3 一句话核心创新（对这类报告而言）

> **第一次把"打包 → 运输 → 送达 → 拆包"这条完整链条，用 8 台异构机器人在一个真实场地里贯通，并把每一环的工程坑逐条记录成可复用的经验。**

## 三、用大白话回答六个问题

### ① 想解决什么问题？

验证"**全机器人门到门配送**"这件事在真实场地里到底行不行，以及**卡在哪**。

### ② 为什么以前不行？

| 原因 | 说明 |
|---|---|
| 单点研究多、链条研究少 | 大家各自做抓取/导航/飞行，没人把 8 台串起来 |
| 异构接口不统一 | 每家的框架不同（ROS1/ROS2/ArmarX/自研） |
| 真实场地限制 | 天气、地板、Wi-Fi、电池、运输损坏 |

### ③ 作者做了什么？

组织黑客松：定场景、定接口、8 队各带机器人、5 天内集成、最后跑一次完整实验。

### ④ 为什么这件事有价值？

- **它证明了"可行"**：18 分钟、无直接人工干预；
- **它暴露了"不可行的地方"**：空中交接要遥操作、开门要遥操作、操作任务慢；
- **它给出了可复用的经验**：下洗气流、泡沫地板、Wi-Fi 干扰、模块化执行器便于更换。

### ⑤ 最后取得什么结果？

8 台机器人接力完成一次配送，18 分钟；两处仍需遥操作。

### ⑥ 最重要的结论是什么？

> **异构系统的瓶颈不在单机能力，而在"接口 + 准备时间 + 兜底机制"。**
> 作者的原话大意：任务在现场定义、没有前期准备，所以这些时间数字**不代表系统极限**——这句话本身就说明了"集成成本"有多高。

## 五、关键要点（可追溯）

### 5.1 八个平台与分工

| 域 | 机器人 | 任务 |
|---|---|---|
| 打包 | **Franka Emika FR3** | 抓物体、装箱、封箱 |
| 运输 | **Centauro**（轮腿 + 双臂） | 搬运包裹 |
| 运输 | **空中操作臂**（多旋翼 + 双臂） | 空中抓取与投放 |
| 运输 | **ANYmal on Wheels**（轮腿四足） | 跨障碍运输 |
| 送达/拆包 | **Rollin' Justin**（人形） | 接收、拆包 |
| 送达/拆包 | **ARMAR-6**（人形） | 接收、拆包 |
| 送达/拆包 | **TIAGo-1**（移动操作臂） | 导航到门口 |
| 送达/拆包 | **TIAGo-2**（移动操作臂） | 开传感器化门 |

### 5.2 逐队教训（§Lessons Learned，最有价值）

| 团队/机器人 | 教训 | 为什么重要 |
|---|---|---|
| **Franka（ISIR-CNRS）** | 依赖**已知 3D 模型 + 仿真物体-夹爪交互**；只处理刚性/半刚性物体 | 物体多样性一上来就不适用（电商/回收场景） |
| **Centauro（IIT）** | 从水泥地进**泡沫地板** → 摩擦骤增 → 腿部关节内应力 → **驱动器温度危险上升** | 轮腿混合对地面变化极敏感 |
| **空中操作臂（USE）** | **下洗气流**在 <1 m 把纸箱吹跑（前 3 次失败）；空箱时**钟摆效应**导致掉落；>5 m 视距人眼分不清末端 | 空中操作的最大敌人是"自己产生的气流" |
| **ANYmal on Wheels（ETHZ）** | 轮腿**速度更高、能耗更低**，但需要**预建图 + 数字孪生** | 性能提升的代价是准备成本 |
| **Rollin' Justin（DLR）** | 需要安全运动生成 + 任务信息交换 | 多机协作的接口问题 |
| **TIAGo-1（IST）/ TIAGo-2（INRIA）** | 导航/开门；跟踪不可靠时的处理 | 真实家居环境的鲁棒性 |
| **ARMAR（KIT）** | ArmarX 认知架构 + RESTful API 做多机协同 | 接口标准化 |
| **总体** | Wi-Fi 与手机移动数据互相干扰 → **要求所有人开飞行模式**；机械损伤（卡车运输 + 软地板）；电池充电要排班 | 真实活动的"非技术"因素 |

### 5.3 结果（§结论）

- **最终实验 18 分钟**；
- **无直接人工干预**，但**空中交接与开门把手用了遥操作**；
- 作者明确指出"**操作类任务需要提速**"。

## 八、我的一句话评价

> **这篇论文的最大价值，是它记录了那些"不会写进方法论文"的东西**：泡沫地板让轮子过热、旋翼把纸箱吹跑、Wi-Fi 被手机干扰、卡车运输震坏关节。
> 而这些恰恰是"具身系统架构"最真实的一面——**在真实世界里，系统失败的原因往往不是算法不够好，而是地板、气流和 Wi-Fi。**
