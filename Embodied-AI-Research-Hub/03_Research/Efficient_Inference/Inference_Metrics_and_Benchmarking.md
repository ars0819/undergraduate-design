# Inference Metrics and Benchmarking

> 本页是**方法备忘/AI 整理**，不是实验结果。任何数字必须来自原始日志。  
> 目标：让“快了多少”这句话有可复核的定义。

## 1. 指标定义

| 指标 | 定义 | 常见错误 |
|---|---|---|
| 模型加载时间 | 从本地文件到模型可前向 | 混入网络下载/解压 |
| 预处理时间 | resize/归一化/tokenize/state 处理 | 只测 GPU，漏 CPU |
| H2D / D2H | CPU↔GPU 传输 | 忘记同步/只测 kernel |
| 骨干延迟 | 视觉语言部分前向 | 与动作头混在一起 |
| 动作头延迟 | diffusion/flow 迭代或 token 解码 | 忽略迭代步数 |
| 新动作块延迟 | 一次真正生成新 chunk 的墙钟 | 把缓存队列弹出当推理 |
| 端到端延迟 | 观测→动作可执行 | 漏后处理/控制 |
| p50 / p95 | 延迟分布的中位数/95 分位 | 只报均值；不报样本数 |
| 吞吐 | 单位时间的新块/动作数 | 把“预测动作数”当“执行动作数” |
| 峰值显存 | allocated/reserved/NVML 分开 | 混用 GiB/GB 或不同进程 |
| 任务成功率 | 成功回合/总回合 | 没有分母、删失败、20 回合称 100% |
| 任务完成时间 | 固定 horizon 内的墙钟 | 失败更快终止被当成高效 |

## 2. 最小测量协议

1. **固定**：代码 commit、权重 revision/hash、processor、数据、输入、dtype、batch=1、noise、执行长度、设备/驱动。
2. **预热**：至少 20 次（按任务调整），不计入正式统计。
3. **计时**：`time.perf_counter()` + 调用前后 `torch.cuda.synchronize()` 得到墙钟；CUDA Events 只作设备归因。
4. **重复**：至少 200 次新块；太慢可降低但如实记录；3 个独立进程/session。
5. **分界**：预处理、H2D、骨干、动作头、D2H、后处理分别测；端到端另算。
6. **显存**：每个配置独立进程；预热后重置 peak；记录 allocated/reserved/NVML。
7. **任务**：固定初态/语言/动作接口；成功数/总数；失败分类；保留视频索引。
8. **原始数据**：保存 CSV/JSONL/日志；图表从原始数据生成，不只保留平滑图。

## 3. “新动作块”与“缓存弹出”

很多策略接口的 `select_action()` 会从动作队列里弹出已经算好的动作。把 50 次弹出取平均，得到的不是网络推理延迟。  
测量时必须：

- 调用真正生成新块的接口（如 `predict_action_chunk()`，以实际代码为准），或
- 在日志中标记 `new_chunk=true/false`，分组统计。

否则会得到“越执行越快”的假象。

## 5. 常见陷阱

- 参数量减少 ≠ 延迟下降；小矩阵可能受 kernel launch/反量化支配。
- 量化省显存 ≠ 加速；没有真实低比特内核时可能更慢。
- 编译的冷启动/重新编译要单独计；只报热态会高估收益。
- profiler 有开销，不能与主计时混在同一次 run。
- 平均延迟会掩盖长尾；机器人控制更关心 p95/最坏情况。
- 跨设备/跨精度/跨 batch 的数字不能直接横比。
- “20 回合全成功”只说明这 20 回合；不能外推真实成功率 100%。

## 6. 最小实验记录字段

- 代码 commit / 未提交改动说明
- Python/torch/CUDA/驱动/GPU 型号
- 权重 revision + 文件 hash
- 数据/任务/初态集 hash
- 输入 schema（图像键/尺寸/state/语言）
- dtype、batch、chunk 长度、执行长度、noise seed
- 计时边界与 warmup/repeat
- 原始延迟文件、显存文件、任务日志、视频索引
- 失败分类与分母
