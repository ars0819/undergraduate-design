# Compression Methods Overview

> 目的：避免把“量化、剪枝、蒸馏、低秩、编译、缓存”混成一个“加速”按钮。  
> 本页不评价具体论文；论文阅读见 [`Papers_Index.md`](../../06_Resources/Papers_Index.md)。

## 1. 一张表

| 方法 | 做什么 | 可能收益 | 主要代价/风险 | 是不是“压缩” |
|---|---|---|---|---|
| 量化 Quantization | 用更低比特表示权重/激活 | 显存/带宽下降；有内核时加速 | 反量化开销、精度损失、内核不支持 | 是 |
| 剪枝 Pruning | 去掉权重/结构 | 稀疏/稀疏内核加速、显存下降 | 不规则稀疏未必加速；精度 | 是 |
| 蒸馏 Distillation | 小模型学大模型 | 小模型容量/速度 | 需要训练、教师数据/算力 | 是（模型变小） |
| 低秩 Low-rank | 用低秩分解近似矩阵 | 参数/计算下降 | 分解误差、额外变换 | 是 |
| 编译 Compile | 图优化/融合/内核选择 | 减少启动/内存访问 | 编译时间、graph break、兼容性 | 否（运行时优化） |
| 缓存 Cache | 复用特征/动作/计算结果 | 重复请求更快 | 命中率、正确性、控制闭环风险 | 否（系统优化） |

## 2. 量化

- **PTQ**（post-training quantization）：训练后量化，成本低；需要校准数据。
- **QAT**（quantization-aware training）：训练时模拟量化，通常更稳，但成本高。
- 权重/激活可以不同比特；对称/非对称、per-tensor/per-channel 不同。
- INT8/INT4 只是存储格式；**有没有高效内核**决定实际速度。
- 对 VLA：动作头、归一化统计、连续动作精度可能比语言骨干更敏感；必须做闭环评测，不只看困惑度/重建。

## 3. 剪枝

- 非结构化稀疏：零散权重；GPU 上未必快。
- 结构化剪枝：删通道/头/层；可能真加速，但改变结构。
- 需要报告稀疏度、内核支持、精度、实际延迟；不要只报参数量。

## 4. 蒸馏与低秩

- 蒸馏需要教师/学生、训练数据、训练预算；本科复现要谨慎评估。
- 低秩分解（SVD 等）可能减少参数，但推理时需要额外矩阵乘/重构；端到端收益要测。
- 对动作头做低秩/蒸馏，可能改变动作分布；闭环成功率是主指标之一。

## 5. 编译

- `torch.compile` 是图捕获 + 后端优化；不是模型压缩。
- 关注：冷启动/首次编译、graph break、动态 shape、额外显存、热态 p50/p95。
- batch=1、短序列、控制闭环下，收益可能与训练吞吐不同。

## 6. 缓存

- 特征缓存、KV cache、动作块缓存是不同东西。
- 动作块缓存可能让 `select_action()` 很快，但没有生成新块；不能当推理加速。
- 缓存要报告命中率、失效条件、对闭环的影响；错误缓存可能造成动作滞后/不一致。

## 7. 选择顺序

1. 先测原始端到端/新块延迟与显存，确认瓶颈。
2. 只选一种方法；固定其他因素。
3. 同时报告：磁盘/显存、延迟、动作误差、闭环成功率、失败类型。
4. 负结果保留；不为了“有优化”而换指标。

## 8. 对当前本科课题的含义

- 首选不是“把模型压到 4bit”，而是先复现官方 `torch.compile` 或 `num_steps` 的推理路径（以实际代码为准）。
- 量化作为有条件扩展：需要真实内核、动作头精度评估、A100/12GB 资源评估。
- 不在 baseline 未跑通时做压缩。
